# vulndb catalog fixes (applied to the live `vulns` DB, tracked here)

The nakon catalog (`configurations` table in the vulndb MySQL) is a shared service, not a repo
file. Script-body fixes applied there are recorded here so they are reviewable and re-appliable.
Apply with an `UPDATE configurations SET script=<file> WHERE name=<name> AND platform=<platform>`.

| name | platform | file | why | applied |
|---|---|---|---|---|
| `local-user` | linux | `local-user-linux.sh` | `usermod -a -G sudo` failed rc=6 on Fedora (no `sudo` group; RHEL/Fedora use `wheel`). Now maps `sudo`↔`wheel` to whatever the box has and creates any other missing group — distro-portable. | 2026-09-28 |
| `sshd-force-sftp-broken-chroot` | linux | `sshd-force-sftp-broken-chroot-linux.sh` | The doc's "fatal config error kills SSH" claim did **not** reproduce on OpenSSH 9.6p1/10.0p2/10.2p1 (`sshd -t` rc=0, restart rc=0). The real defect: `Match Group sftpusers` was planted without ever creating the group, so the block could never match a user and the plant was inert. Now creates the group (repairs an existing broken plant), validates with `sshd -t` before touching the daemon, detects the `ssh`/`sshd` unit instead of guessing, and propagates the reload rc. Finding verified live via `sshd -T -C user=<member>`. | 2026-10-02 |
| `tftpd-hpa-anon-write` | linux | `tftpd-hpa-anon-write-linux.sh` | The doc's "postinst exit 82 wedges dpkg on Noble" claim did **not** reproduce (`dpkg --audit` empty, `dpkg -C` rc=0). The real defect: the package postinst starts the daemon with shipped options (`in.tftpd --secure /srv/tftp`) and `systemctl enable --now` is a no-op on a running unit, so the rewritten `/etc/default/tftpd-hpa` was never loaded and anonymous WRITE was refused (curl rc=68) — an inert plant. Now restarts the unit, sets the keys unconditionally, injects `-s -c -p` through a systemd drop-in on RHEL/Fedora's socket-activated `tftp.service`, asserts dpkg is clean, and performs a real unauthenticated upload+download round trip. | 2026-10-02 |
| `postgresql-no-auth` | linux | `postgresql-no-auth-linux.sh` | Reproduced on noble/debian13/fedora44. RPM path ran the Debian-only `pg_ctlcluster $(pg_lsclusters ...) init` (`pg_lsclusters: command not found` on Fedora → cluster never initdb'd, service `failed`, no socket/port), unit names were guessed and every failure swallowed by `|| true`, and `sed 's/^local.*all.*all.*peer/'` never matched the shipped `local all postgres peer` line so `psql -U postgres` still failed "Peer authentication failed". Now initializes the RPM cluster (`postgresql-setup --initdb`), rewrites every `local`/loopback line for db `all` to `trust` regardless of the shipped method, detects the real unit, polls `pg_isready`, and asserts a real no-password `psql` connect. Verified off-box with the raw v3 protocol (`AuthenticationOk`). | 2026-10-02 |
| `postgresql-remote-access` | linux | `postgresql-remote-access-linux.sh` | Reproduced on noble/debian13/fedora44. `sed "s/^#*listen_addresses=.*/listen_addresses = '*'/"` requires key and `=` to be adjacent, but every shipped `postgresql.conf` writes `#listen_addresses = 'localhost'` (with spaces) — so the edit silently no-opped, the server stayed bound to loopback and the whole network-trust finding was absent (`Connection refused` from the box's LAN address). Now edits by pattern with optional whitespace, appends canonical `::/0` (was `::0/0`) idempotently, detects the unit, polls `pg_isready`, and asserts a real unauthenticated psql connect to the box's own LAN address. `depends_on: [postgresql-no-auth]` kept. | 2026-10-02 |
| `unrealircd-backdoor-container` | linux | `unrealircd-backdoor-container-linux.sh` | Reproduced on 125: `docker: command not found`, rc=127, no container, 6667 dead. Now detects docker/podman, installs a runtime via the box's own package manager (`docker.io` / `moby-engine` / `docker` / `podman-docker` / `docker` on apk), waits for the daemon, and when no runtime can be obtained fails **rc=1 with an actionable "MISSING DEPENDENCY" message — never a bare 127**. Asserts the container is running and 6667 accepts TCP. Finding verified live (impersonating name/tag/label + `uid=0(root)` shell over 6667, also from off-box). | 2026-10-02 |
| `local-user-win` | windows | `local-user-win.sh` | Handoff item 5's "`Set-LocalUser`/password-policy failure on the account its own config creates" did **not** reproduce: the body already creates the account first (`Get-LocalUser` guard → `New-LocalUser`) and a second consecutive run is rc=0. The real defect: `PASSWORD_NEVER_EXPIRES -eq 1` compares a *string* ("`1`", as nakon renders every var) against an *integer*, so the flag silently no-opped and `net user <u>` stayed `Password expires 11/13/2026`; the flag was also only applied on the create path. Now compares `-eq '1'` and re-asserts both flags after either path. `ADMIN_ADD` worked (`'1' -eq 1` coerces the right operand, so it was never the bug). Finding verified live (`net user` → `Password expires Never`, account enabled, member of Administrators, FullName/Description set) over two consecutive runs. | 2026-10-02 |
| `powershell-execution-unrestricted` | windows | `powershell-execution-unrestricted.sh` | Reproduced as rc=1, **not** a `Set-LocalUser`/password-policy failure (the row touches no account and no password policy). nakon launches each step with `-ExecutionPolicy Bypass`, i.e. a Process-scope policy more specific than LocalMachine; `Set-ExecutionPolicy -Scope LocalMachine` then raises a *terminating* `SecurityException` ("overridden by a policy defined at a more specific scope") that `-ErrorAction Ignore`, `-ErrorAction SilentlyContinue` **and** `try/catch` all leave in `$Error` (verified on 5.1.20348 — every variant leaves `$Error.Count=1`), so nakon scored rc=1 and the three registry writes below it never ran. Now writes the LocalMachine policy value straight into `HKLM:\SOFTWARE\Microsoft\PowerShell\1\ShellIds\Microsoft.PowerShell\ExecutionPolicy` (a `reg export` diff proves that is the only value `Set-ExecutionPolicy -Scope LocalMachine` touches) plus the `Policies\...\PowerShell\EnableScripts` value, both `-Force`. Finding verified live: `Get-ExecutionPolicy -Scope LocalMachine` = `Unrestricted`, `EnableScripts` = 1, rc=0 on two consecutive runs from an undefined policy value. | 2026-10-02 |
| `rpc-proxy-on-dc-web-win` | windows | `rpc-proxy-on-dc-web-win.sh` | Reproduced on a box with IIS + `RPC-over-HTTP-Proxy` installed: the row is **not** an account/password-policy failure at all, but it was dirty — `Install-WindowsFeature RSAT-Rpc-Proxy` names a feature that exists on no Server SKU, so nothing was ever installed, and `poolManagementMode` is not an IIS application property, so `Set-WebConfigurationProperty` emitted `Target configuration object '.../applications[@name="/Rpc"]' is not found` on every run. `/Rpc` + `/RpcWithCert` did get created and the `RPCPROXY` ISAPI handler was mapped. Now installs the real role (`RPC-over-HTTP-Proxy`) and only when absent, throws an actionable message when the declared `IIS HTTP` prerequisite (`W3SVC`/`WebAdministration`) is missing instead of a raw command-not-found, keeps `-Force` app creation (also authoritative for the app pool), re-asserts `HKLM:\SOFTWARE\Microsoft\Rpc\RpcProxy` `Enabled` and `ValidPorts` (an empty `ValidPorts` leaves a shell that cannot proxy anything), and suppresses the `Set-ItemProperty` result object. Finding verified live: `/Rpc` + `/RpcWithCert` at `%windir%\System32\RpcProxy` on `DefaultAppPool`, `RPCPROXY` handler present, `ValidPorts=WINDOWS-UOSF89N:593;WINDOWS-UOSF89N:49152-65535`, rc=0 twice. | 2026-10-02 |
| `unauth-kiosk-app-startup-win` | windows | `unauth-kiosk-app-startup-win.sh` | Two runs measured. (a) **Prerequisite met, port free** (real app tree: CPython 3.11 venv with uvicorn + `main.py`): the current body already works — `0.0.0.0:80` listening, `HTTP 200 {"kiosk":"unauthenticated"}`, rc=0, and a consecutive re-run is also rc=0. (b) **Prerequisite absent** (no `C:\KaminoAI\app` tree, no `python` on PATH): the body died with `Start-Process : Cannot validate argument on parameter 'FilePath'. The argument is null or empty`, i.e. a prerequisite gap reported as a script bug, since `(Get-Command python -EA SilentlyContinue).Source` is `$null` and is handed straight to `Start-Process`. It also silently returns rc=0 when a conflicting listener (IIS/http.sys) already owns the port, so the kiosk is not actually scoring. Now throws an explicit "no python interpreter for the kiosk app: neither '<APP_DIR>\.venv\Scripts\python.exe' nor 'python' on PATH exists. Plant the kiosk app tree (or set APP_DIR)" and warns (does not throw — the fragility is the finding) when nothing is listening on `$PORT` after 8s. Finding verified live in the met case: `0.0.0.0:80` + `HTTP 200 {"kiosk":"unauthenticated"}` over two consecutive runs. | 2026-10-02 |
| `mailenable-cleartext-mail-win` | windows | `mailenable-cleartext-mail-win.candidate` (**NOT applied**) | The row does **not** install MailEnable: `choco install mailenable` fails because the `mailenable` package does not exist in the community repo (`choco search mailenable --exact --limit-output` returns nothing; `choco search mail` shows many mail packages and no MailEnable) — that is a wrong-package-ID script bug, **not** the environmental network/TLS failure the handoff anticipated (TLS 1.2 install of Chocolatey 2.7.4 succeeded and `https://community.chocolatey.org/api/v2/` answers 200). `Set-Service`/`Start-Service` on absent services are `-EA SilentlyContinue` no-ops and only the `MailEnable-Cleartext` firewall rule really lands, so the cleartext POP3/IMAP weakness is absent from the box. The candidate records the working acquisition (`https://www.mailenable.com/MESetup.exe`, 29.5 MB, valid Authenticode) and the correct service names (`MEMTAS`/`MEPOPS`/`MEIMAPS`, not `MESMTPC`/`MEIA`/`MEPOP3S`), but `/S` on that Wise installer only completes the MAPI-connector component (no services, empty `Bin`), and the full mail-server component needs its interactive installer. Left unapplied and classified CANNOT TEST IN BUDGET — see the file header. | — |
